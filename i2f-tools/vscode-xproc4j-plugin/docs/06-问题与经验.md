# 问题与经验总结

> 项目：vscode-xproc4j-plugin
> 记录范围：需求分析、设计、编码、测试与打包阶段的问题、根因、修复与可复用经验。
> 维护规则：新问题在解决后立即追加；不要把文档正文、属性值、SQL 文本或凭据写入本文件。

## 1. 结论摘要

1. VS Code 没有与 IntelliJ `MultiHostInjector` 等价的一等语言注入 API，最终采用「TextMate 注入语法 + 语义 token 兜底 + 语言服务复用」的组合，并在设计阶段为每项能力保留降级路径。
2. 扩展标识由 `package.json` 的 `publisher + name` 决定；把 `name` 定为 `xproc4j` 后，实际 ID 才是 `ice2faith.xproc4j`。
3. 补全上下文的最大风险不是候选生成，而是「从光标向前找 `<`」的边界判断；行首裸 `<`、SQL 比较符、结束标签起点都是必须覆盖的回归点。
4. 生成物必须可重复：报告中的时间戳、绝对路径会破坏 `gen:check`，已改为确定性输出。
5. 打包前的 `vsce` 校验会因相对链接与缺失 `repository` 字段失败；无远端仓库时应显式使用 `--allow-missing-repository`，README 避免相对 Markdown 链接。
6. 自定义 TextMate scope 的主题兼容性不能只靠语法测试：`variable.other.xproc4j` 在 VS Code Light 主题下被 `variable.other` 规则压成正文色，变量看似未高亮；改用 `support.variable.xproc4j` 后解析为蓝色 `#0550AE`，与括号/标点一致且醒目。

## 2. 问题清单

| 编号 | 现象 | 根因 | 修复 | 经验 |
|---|---|---|---|---|
| I-01 | DTD 无法直接作为严格 schema | 19 条 ATTLIST 异常：18 条缺类型、1 条非法类型 `lang-shell result trim` | 解析器按 `CDATA` 容错，逐条写入 `metadata/report.md` | 上游 DTD 只能当元数据源；解析器必须容忍缺类型与未知类型 |
| I-02 | TextMate 正文注入会消费开始标签，属性值高亮失效 | 注入规则从 `<tag>` 起匹配，属性捕获落入注入范围 | 开始标签内单独生成属性/feature 规则；属性值变量由语义 token 兜底 | 注入边界应尽量从 `>` 之后开始；无法避免时用语义 token 补位 |
| I-03 | 多行开始标签可能丢失正文注入 | TextMate 的 `begin/end` 以行为单位推进，跨行开始标签匹配不稳定 | 记录为已知限制；正文变量仍由语义 token 着色 | 生成语法必须为「少量写法降级」留出说明，不应承诺 100% 覆盖 |
| I-04 | 第三方语言（Groovy/VTL/FreeMarker/Thymeleaf/SpEL）注入不稳定 | VS Code 不自带这些语法，scope 名取决于用户安装的扩展 | 生成规则引用常见 scope；未安装时自然降级为文本 | 不要硬依赖第三方扩展；能力发现应保持可选 |
| I-05 | 集成测试报告扩展未安装 | `package.json` 的 `name` 原为 `vscode-xproc4j`，实际 ID 是 `ice2faith.vscode-xproc4j` | 将 `name` 改为 `xproc4j`，同步详细设计 §2.2 | 扩展 ID 以 `publisher.name` 为准；测试断言必须与清单一致 |
| I-06 | 标签补全在「行首裸 `<` 后换行」时无候选 | `findStartTagOffset` 要求 `<` 后必须是标签名首字符，换行被拒绝 | 允许 `<` 后为空白，但仅当 `<` 独占行首（前缀全为空白） | 裸 `<` 是合法的输入中间态；同时要防止 SQL 的 `<` 比较符误触发 |
| I-07 | SQL 正文 `a < b` 被误判为标签 | 修复 I-06 后，只要 `<` 后可跟空白就会被接受 | 增加行首前缀判断；新增 SQL 比较符回归测试 | 上下文判断要同时覆盖「正向合法」和「反向误判」 |
| I-08 | `${co` 位于结束标签前时变量补全返回空 | `isInsideClosingTag` 使用 `offset >= endTagStart`，光标正好在 `</tag>` 的 `<` 之前被算作标签内部 | 改为 `offset > endTagStart` | 区间边界必须用测试钉死；`>=` 与 `>` 的差异会直接吞掉补全 |
| I-09 | `gen:check` 每次失败 | 报告含 `new Date().toISOString()` 与绝对源路径 | 移除时间戳、改用相对源目录，重新生成后校验通过 | 生成物校验的前提是确定性；任何时间/绝对路径都不能进入受校验产物 |
| I-10 | TypeScript 编译错误：`Thenable` 无 `catch` | VS Code 的 `FileStat` 等 API 返回 `Thenable`，不是完整 Promise | 改为 `try/catch` + `await` | 适配层尽量使用 `async/await`，不要假设 Thenable 具备 Promise 全部方法 |
| I-11 | `SemanticTokensBuilder.push` 重载不匹配 | 传入了 `Range + number + number`，而当前类型定义要求 token type 字符串重载 | 使用 `push(range, type, modifiers)` 字符串重载 | 语义 token 的 tokenType 必须来自 legend 顺序；类型与 legend 要集中定义 |
| I-12 | 补全/导航把 `IndexService` 传给只接受 `IndexQuery` 的领域函数 | 领域层只依赖查询接口，服务层还承担生命周期 | 领域函数传 `index.store`；就绪等待单独传 `readiness` | 领域层接口要最小化；生命周期与查询职责分离 |
| I-13 | `readAndIndex` 返回 `PromiseLike` 导致类型不匹配 | 方法内部返回对象但声明为同步/非 async | 改为 `async` 方法 | 只要内部有 `await`，入口就应显式 `async` |
| I-14 | `index-service.ts` 放在 `domain/index` 违反「领域层零 vscode」 | 服务直接使用 `vscode.workspace`、`FileSystemWatcher` 等 | 移动到 `src/infrastructure/index-service.ts` | 分层不是目录装饰；发现依赖方向错误应立即迁移 |
| I-15 | 索引实现与详细设计的「轻量 sink」不一致 | 为保证正确性直接复用了完整扫描器 | 记录偏差；当前以正确性和可维护性优先 | 性能优化应在有基准与测试后替换，不要提前引入第二套解析器 |
| I-16 | `vsce package` 报 `NOTICE` 相对链接损坏 | 没有 `repository` 字段，vsce 无法生成绝对链接 | README 改为纯文本引用 `NOTICE`/`LICENSE`；打包脚本加 `--allow-missing-repository` | 无远端仓库时不要使用相对 Markdown 链接；打包命令要可重复 |
| I-17 | 集成测试临时目录清理报 EPERM | Windows 上 VS Code 进程退出后仍短暂持有 profile 目录 | `rmSync` 增加 `maxRetries/retryDelay`，失败时交给系统清理 | Windows 文件句柄释放有延迟；测试清理必须可失败降级 |
| I-18 | 语法文件实际体积大于生成器统计 | 生成器统计的是紧凑 JSON 字节数，磁盘文件是格式化 JSON | 文档以实际 VSIX 内容为准；统计值仅作生成期参考 | 体积指标要说明口径；发布检查以 VSIX 实际大小为准 |
| I-19 | 新建文件命令使用 `WorkspaceEdit.createFile` 覆盖行为不确定 | 不同 VS Code 版本/文件系统对 `overwrite/ignoreIfExists` 处理不同 | 先做存在性检查与模态确认，再 `createFile({ overwrite: true })` + `insert`，失败给出明确错误 | 破坏性操作必须二次确认，并在写入前做竞态复查 |
| I-20 | 二次打包时旧 `SHA256SUMS.json` 被塞进 VSIX | 校验和写在 `dist/`，`.vscodeignore` 只排除 source map 与 TS | 在 `.vscodeignore` 排除 `dist/SHA256SUMS.json`，重新打包并校验文件清单 | 发布产物与辅助产物必须分区；打包前检查 VSIX 文件列表 |
| I-21 | `${}`、`#{}`、`$!{}` 变量在真实文件中看似未高亮，用户进一步要求与括号同色 | 变量 scope 使用 `variable.other.xproc4j`；VS Code Light（2026 默认）把 `variable.other` 映射为正文色 `#1f2328`，覆盖了 `variable` 的橙色；`variable.parameter` 虽恢复可见但为橙色，与用户期望的括号蓝不一致 | 语法与 `semanticTokenScopes` 统一改为 `support.variable.xproc4j`；用实际主题计算 token 颜色验证为 `#0550AE` | 自定义 token scope 不能只看语义层级，还要检查主流主题的父级 scope 是否把它压成正文色；醒目度应按用户期望的相邻视觉元素校准，而不是只选「能看见」的 scope |
| I-22 | `samples/` 被自动打进 VSIX | `.vscodeignore` 未排除新增目录 | 增加 `samples/**`，重新打包确认文件数回到 10 | 新增顶层目录后必须检查 `vsce ls`/VSIX 清单，尤其不能把用户真实业务文件带入发布物 |
| I-23 | 同为 XML 属性名，有的高亮、有的不高亮，颜色在红/蓝间混用 | 三个独立原因叠加：① 非正文标签用窄规则 `(<)(tag)` 先消费了 `<tag`，宿主 XML 语法不再进入 `meta.tag`，后续属性名失去 scope；② procedure 开放参数/动态属性用 `variable.parameter.xproc4j`，主题映射为橙色；③ SQL 正文中的 `<sql-dialect>` 未先于 `source.sql` 匹配，被 SQL 当成比较符/标识符 | ① 用 `startTagRule` 的 begin/end 覆盖整个开始标签，属性段复用 `attrsPattern`，属性可跨行；② 开放参数 scope 改为 `entity.other.attribute-name.xproc4j`；③ 在 `#sqlContent` 最前面加入 `sql-dialect` 的 XML 规则。新增两条语法回归 | 注入语法一旦消费宿主标签的起始符号，就必须自行补齐该标签的完整结构（名称、属性、结束），不能假设宿主语法会续接；正文注入中若允许嵌套 XML 子标签，必须把这些标签排在宿主语言 `include` 之前；同类视觉元素应统一 scope，而不是按代码路径各用一套 |
| I-24 | 想让 SQL 与 `lang-eval*` 正文区域显示整行背景色、属性值显示更浅背景，并按类型区分 | VS Code 不渲染 TextMate/语义 token 规则里的 `background`；`editor.tokenColorCustomizations` 设置 background 会告警，主题层也拿不到稳定块范围 | 新增纯领域函数计算嵌入块正文范围并标注 `sql`/`eval`，适配层按类型用 `TextEditor.setDecorations(..., { isWholeLine: true, backgroundColor })` 绘制（SQL 浅黄、eval 浅绿）；属性值复用同一装饰器，取扫描器 `valueRange`（不含引号）精确绘制，空值跳过；同类型合并嵌套范围避免叠色；200 ms 防抖并在可见编辑器切换时重绘 | 需要“块级”视觉效果时不要试图改 token 配色，直接用装饰 API；按类型创建独立 decoration type，不要在同一范围叠加多个半透明背景；属性值背景应使用解析器给出的值范围，不要用正则重新解析；装饰范围应由文档模型计算，而不是扫描可见文本 |
| I-25 | 要求 `lang-eval*` 正文关键字固定为 dodgerblue，但注入语法与主题映射无法保证颜色 | TextMate/语义 token 的 `foreground` 受主题规则与父级 scope 影响；改 token 颜色只能靠 `editor.tokenColorCustomizations`，会覆盖用户主题且难以只作用于目标块 | 新增纯领域函数 `collectEvalKeywordRanges`，按 `\b(?:...)\b` 在 `lang-eval*` 正文内匹配 Java/JavaScript/SQL99 联合关键字；适配层用 `TextEditor.setDecorations(..., { color: '#1E90FF' })` 精确覆盖关键字范围；独立开关与 200 ms 防抖复用现有装饰器 | 需要“固定颜色”而不是“跟随主题”时，应使用装饰强制 `color`，不要依赖 token scope；正则匹配只保证词边界，字符串/注释中的关键字也会命中，需在文档中标注；装饰只覆盖关键字本身，避免破坏注入语法的其他 token |
| I-26 | 把 `$` 变量高亮扩展到 YAML/Java 时，若再注册语义 token Provider，会压掉语言扩展自带的 token | VS Code 同一语言只采用评分最高的语义 token Provider，多个 Provider 不合并；扩展注册 YAML/Java Provider 会与内置/第三方 Provider 竞争，导致原有语义高亮消失 | XML 仍用语义 token 并按 `variableHighlight.extensions` 是否含 `xml` 决定是否输出变量 token；非 XML 改用 `RawVariableHighlightDecorator`，按可见编辑器与主题用装饰着色（Light `#0550AE` / Dark `#9CDCFE`），后缀由 `normalizeFileExtensions` 归一化 | 给“别人的语言”增加语义高亮时，先确认 Provider 竞争规则；不能合并 Provider 的场景应选装饰；装饰要按主题重建颜色，并在可见编辑器、文档变化、配置变化时重绘 |
| I-27 | 要求 `lang-eval*` 数值呈蓝色、字符串呈绿色，但字符串内的数字/关键字会被其他装饰二次染色，且绿字与浅绿背景可能分不清 | 数值与关键字各自用正则独立匹配，`"12.5"`、`"select"` 会同时命中两种规则；单一固定绿色无法同时保证 Light（浅绿背景）与 Dark（深色背景）的可读性 | 领域层先收集字符串范围作为保护区，数字与关键字跳过保护区内的匹配；适配层按主题选明度：Light `#1565C0`/`#2E7D32`、Dark `#90CAF9`/`#81C784`，主题变化时重建 decoration type | 多类前景装饰共享同一文本范围时，要先定保护优先级，避免叠色；颜色要与相邻背景元素做明度对比，固定单一色值在 Light/Dark 下通常不可兼得 |

## 4. 设计偏差记录

| 偏差 | 设计原稿 | 实际实现 | 原因与处理 |
|---|---|---|---|
| 索引服务位置 | `domain/index/index-service.ts` | `infrastructure/index-service.ts` | 直接依赖 `vscode`，必须留在基础设施层；已同步详细设计目录说明 |

## 5. 待办与风险

- 发布前人工检查：真实编辑器中的注入配色、POM/Spring/MyBatis 无污染、第三方语言缺失时的降级、语义 token 与 Red Hat XML 等扩展叠加。
- 语法文件约 1.12 MB（VSIX 内格式化 JSON；生成器紧凑统计 631 KB），首次 tokenization 约数百毫秒量级；若后续扩展到更多标签/语言，需要引入规则预算与基准测试。
- 索引服务依赖 VS Code API，当前由集成测试覆盖；如后续需要单测，应抽出 `WorkspacePort` 接口。
- 上游 `procedure.dtd` 的 19 条异常声明由报告持续记录；若上游修订，需要重新生成并复核。
- 无远端仓库时 `vsce` 会警告缺少 `repository`，当前通过 `--allow-missing-repository` 打包；正式发布前应补充真实仓库地址。

## 6. 可复用检查清单

1. 改动补全上下文：至少覆盖裸 `<`、行首 `<`、SQL `<`、结束标签边界、注释/CDATA、多行开始标签。
2. 改动索引：覆盖覆盖层优先、关闭恢复磁盘、删除/重命名、文件上限、超大/二进制跳过、当前文件优先排序。
3. 改动生成器：执行 `npm run gen` 后必须执行 `npm run gen:check`，确认无时间戳与绝对路径。
4. 改动打包配置：执行 `npx vsce ls` 或检查 VSIX 清单，确认 `dist/extension.js`、syntaxes、snippets、LICENSE、NOTICE、README、CHANGELOG 均在内。
5. 发布前：`npm run check`、`npm run test:integration`、VSIX 安装冒烟与 SHA256 校验缺一不可。
6. 调整语法 scope 后：用真实主题计算一次 token 前景色（或人工目测），确认不会被父级 scope 压成正文色；变量至少覆盖 `${}`、`#{}`、`$!{}`、`#!{}`、短变量与空占位符。
