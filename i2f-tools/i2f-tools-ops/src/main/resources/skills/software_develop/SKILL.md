# 软件开发

- 通过规范性的开发方法论，指导编写合规、安全、高性能、具有生命力、具备可持续发展、高可维护性的软件
- 明确以下核心问题
    - 软件的定义
    - 软件的组成（交付产物）
    - 需求分析
    - 概要设计
    - 详细设计
    - 编码与实施
    - 测试与回归
    - 部署与运维
    - 开发指导说明
    - 用户使用手册
- 最终输出一下产物或文档
    - 软件=程序+数据+文档

## 软件的定义

- 软件是指为了满足用户特定需求，进行设计开发的一个完整运行的程序

## 软件的组成

- 软件主要包含程序、数据、文档
- 程序是，实际可运行的程序
    - 包括编译型、解释性等各种形态
    - 通常还包括源代码
- 数据是，程序运行时需要使用的数据，包括初始化、运行期、维护期所必须的数据
    - 初始化期间，包括配置文件、环境配置、初始化脚本（例如数据库脚本）等
- 文档是，用表对程序的使用与维护进行完善表示的文档资料
    - 通常包括两个部分
    - 一个是，面向用户的用户操作手册（或使用说明书）
        - 用于帮助用户了解与使用程序
        - 目的是教会用户正确使用程序
    - 另一个是，面向软件维护人员（程序员、运维工程师等）的开发技术文档
        - 用于帮助开发者快速入手了解软件设计
        - 目的是教会开发者进行可持续开发
- 【重要】因此，一个软件最基础交付产物的也是这几个部分

## 需求分析

- 需求分析时对用户提出的软件最终目标的逐步拆解分析
- 了解目标软件要完成的功能、系统边界、参与方、达成的目标
- 功能性需求（要完成的基础功能）与非功能性需求（性能、安全性等方面）
- 需求分析的目的，是了解用户目标，并帮助用户逐步明确真真的核心需求
- 因为，用户的需求通常是模糊的、不明确的、待完善的
- 因此，需求分析就需要逐步明确、消除不明确、细化需求，转换为可实施的软件开发
- 同时，用户常常只考虑目标、而不清楚软件实现上的内容
- 因此，需要提供一些技术上可行的方案，让用户做选择，而不是让用户给出解决方案
- 同时，需要给出方案需要的成本、时间等维度提供给用户进行参考
- 【重要】核心就是，采用多轮次，用选择题的方式，引导用户完成需求明确工作，与初步大致的功能性与非功能性需求
    - 功能性需求是最重要的，一个系统的可用性是第一优先级
    - 非功能性需求是次要的，只有先完成功能性需求的前提下，保证可用性，再尽量完成非功能性需求（安全、性能等）
- 【重要】比较重要的是，软件最终的运行环境是什么，这将是非常重要的，决定了应该使用什么技术方案、什么实现方式
    - 比如，运行在什么系统上（windows/linux等）,呈现方式是什么（浏览器/小程序/桌面客户端/移动客户端等）
    - 目标用户群体是什么（普通群众、专业业务人员、技术人员等）
    - 这些都在不同的程度上，决定了软件的形态和偏重

## 概要设计

- 概要设计，是对需求的结果，进行大致开发工作的蓝图设计
- 现代开发中，主要从以下几个方向进行考虑内容
    - 业务流
        - 理清软件主要实现的主要业务流有哪些，流程之间的流转关系
        - 这是软件的核心功能诉求
        - 梳理业务流的运作方式，工作流之间的关系（协作、限制、互斥、依赖等）
    - 数据流
        - 从数据流转的角度，对软件系统进行建模
        - 了解软件初始化、运行等期间使用的数据流转方式、变换关系
    - 状态转移
        - 一个软件，通常都会设计到状态的转移
        - 理解状态转移规则、限制
        - 从而了解整个目标软件的核心数据、业务的运行模式
    - 参与方
        - 软件参与方，也就是参与使用、组成、连接软件的相关方
        - 包括人员、三方系统、三方软件等
        - 它们表述了软件运行所参与的一些实体
        - 这是划定系统边界的一个核心要素
    - 软件架构选型
        - 根据用户目标需求、业务流、数据流、状态转移、参与方等信息
        - 综合考量选取合适的软件架构类型（或混合软件架构模式）
        - 优先选取现代化的软件架构，使用现代化的开发技术方案
            - 比如：springboot,springcloud,vue,react,flask等
        - 呈现模式，简单单体程序、CS程序、BS程序、IOT程序等
        - 架构模式，MVC程序、MVVC程序、DAO程序等
        - 优先考虑开源宽松商业限制的协议
        - 同时，需要考虑使用的编程语言，语言的版本限制等要求
            - 比如，使用Java的话，使用jdk多少的版本
    - 中间件选型（根据需要决定）
        - 依据架构类型，选择合适的中间件，如果不需要中间件可以不考虑
        - 采用现代化的开源宽松中间件
        - 比如常见的中间件：redis,zookeeper,kafka等
    - 依赖组件选型（根据需要决定）
        - 根据架构类型、中间件，就已经初步决定了使用的技术方式和使用的技术手段
        - 这样，也就大致决定了使用的依赖组件有哪些
        - 如果有这样的依赖组件能够满足需求，那就不应该新创建一个这样的轮子
        - 应该直接使用哪些被广泛使用、经过充足验证的依赖，而不是自己写一个
        - 因此，选择最合适的依赖组件完成软件目标就十分重要
        - 比如java常用的Maven依赖、gradle依赖
        - 或者Python用的pip依赖等

## 详细设计

- 详细设计，是对概要设计的细化，决定了实施工作的骨干，具体走向
- 现代开发中，主要从以下几个方向进行考虑内容
    - 模块设计
        - 一个良好的具有生命力的软件设计，一个合理的模块设计是必不可少的
        - 模块设计的目标是，提升编码或构建的可复用性、可维护性、可读性
        - 好的模块划分，是便于理解的，便于复用的
    - 设计模式选型
        - 一个好的编码，目的是为了更好的修改或者变更，而不产生副作用
        - 选择合适的设计模式，是软件可维护性、可读性的必要条件
        - 正确使用23种设计模式，选取或组合最合适的设计模式进行编码
    - 核心算法与数据结构选型
        - 使用合适的算法或数据结构，解决同样的问题，是知识的直接复用
        - 比如使用经典算法与数据结构直接解决问题
        - 或者在 leetcode 等平台存在的算法与数据结构，使用这些经典解决方案，直接解决问题
        - 比自己独自思考、新造轮子更可靠
    - 数据持久化选型
        - 数据持久化，在软件开发中是比较常见的需求
        - 包括业务数据、状态数据、日志数据、审计数据等
        - 持久化方案，应该根据软件要达成的目标，选择或组合合适的持久化方案
        - 比如文件存储、SQL数据库、NOSQL数据库、分布式文件系统、对象存储等
    - 界面设计
        - 再大多数的软件开发中，界面设计是必不可少的
        - 界面设计应该美观、简洁，具有自描述性，操作简单，操作连贯
            - 可以考虑页面漫游式的引导，或者首次使用引导
        - 使用现代UI美学设计方案，美观简洁
        - UI具有自描述性质，能够从UI的布局，操作提示，能够轻易学会软件操作，理解软件操作
        - UI操作应该简单，能够让软件提供的操作或者输入，都应该由软件实现或完成
        - 操作连贯，当在一个业务流中，上下操作之间的切换应该连贯，而不是再不同的菜单之间来回手动切换
        - 防呆设计，应该对敏感操作、危险操作进行防呆设计，避免误操作，并且给出明确的操作确认提示
            - 比如删除、扣款、转账等，都应该至少具备二次确认操作
    - 故障与恢复方案设计
        - 目标运行环境或者使用人员，都是不能够确定的
        - 因此，软件发生故障时，不管是因为软件运行环境（崩溃、蓝屏、断电等）造成的软件运行故障
        - 都应该设计响应的恢复机制，让软件能够完成最大限度的自愈
        - 保证软件的可用性和可靠性

## 编码与实施

- 软件编码与实施阶段，是软件开发的主要阶段，是将设计阶段的内容，转换为软件程序的工程
- 做到，代码就是文档，代码的自描述性；划分就是设计图，从划分能够看出理念设计、思路
- 现代开发中，主要从以下几个方向进行考虑内容
    - 模块化
        - 划分合适的软件模块，保持每个模块下的源代码数量不多
        - 能够直接从软件模块的划分上，大致看出承载业务、提供能力、设计模式、包结构、抽象与实现、拓展点等
        - 这样的模块划分才是一个合规的划分
        - 保持每个模块下的源代码尽量少，模块下的依赖源代码应该放到子模块中
            - 一些语言中，这种属于 package 或者 module 的概念
            - 以 Java 为例，一个 package 下面不应该包含较多的源代码
                - 而是应该只包含模块直接入口的源代码，内部依赖的源代码，拆分到子 package 中
                - 也就是最少知识原则
    - 健壮性
        - 对输入做必要的校验，防止不合法、不合理的输入，并且给出明确的错误提示
        - 使用卫语句，提前在函数内进行前置检查，规避不正确的输入
        - 错误应该具有明确的错误提示，以及可能得改正提示信息
        - 这将有助于开发人员、运维人员、使用用户改正或反馈
    - 可读性
        - 合理拆分源代码，保证单个源代码文件不宜过长，例如超过1000行
        - 合理拆分函数，保证单个函数不宜过长，例如超过100行
        - 合理提取常量，避免魔法值难以理解
        - 合理抽取公共函数，避免重复代码
        - 合理使用设计模式，避免维护地域
        - 合理使用算法与数据结构，复用成熟实现方案，避免单独创造
        - 使用卫语句，避免深层嵌套
        - 使用continue/break，避免深层嵌套
        - 使用函数抽取，避免深层嵌套
        - 重要逻辑、关键常量、易混淆、反常识编码内容等，必须添加注释解释
            - 重要逻辑，比如：复杂的逻辑或流程，或者关键位运算
            - 关键常量，比如：常量为什么是这样一个值，为什么进行这样的运算
            - 易混淆，比如：为什么单独使用一个副本
            - 反常识，比如：为什么使用反常识的编码方式，例如使用 == 而不是 equals
    - 可维护性
        - 使用合理且合适的设计模式，而不是直接堆砌式编码
        - 能够使用现有成熟方案或者依赖库的，应该直接使用，而不是单独创造
    - 编码质量
        - 使用语义化的命名，变量名、函数名、参数名等，都应该使用语义化的命名方式
            - 比如使用了设计模式，那么就应该尽量使用这个设计模式中的命名习惯，例如factory,facade等
        - 同时避免复杂化命名，比如非嵌套循环的循环变量，若无太多实际意义，就应该保持变量名简洁
            - 比如for,for-range循环中的迭代变量
        - 再一些编程语言中，类似是弱化的，如果其编程语言或IDE提供了注释辅助类型的情况下，应该添加类型注释
            - 例如，在 javascript 中，可以通过 @type 等进行标注类型
    - 编码风格
        - 保持项目内编码风格统一，避免不同的编码风格堆砌，造成可读性障碍
        - 保持引用依赖统一，避免为了完成同一个功能，再不同地方使用不同的依赖完成，造成依赖混乱
        - 比如，在Java项目中，都使用lombok完成pojo的模板代码
        - 再比如，在springboot的mvc开发的ssm项目中，模块划分、包划分、类名规则统一
    - 充分测试
        - 至少保证核心算法、核心业务、关键模块具有完善充分的测试，保证软件质量
    - 性能优化
        - 再编码时，再完成业务逻辑的基础上，应该考虑性能问题，进行性能优化
        - 比如，使用缓存避免反复解析、避免重复读取，例如一些代价较高（占IO、内存、CPU、网络等）
        - 再比如使用读写锁、乐观锁等降低锁的粒度，避免忙等或剧烈的锁竞争
        - 或者使用线程池、多线程技术提升性能
        - 【重要】但需要保证业务逻辑不变或在可接受范围内
    - 线程安全
        - 在进行多线程开发、WEB开发时，常常还需要考虑线程安全的问题
        - 应该要杜绝出现线程不安全的情况，保证线程安全
        - 合理使用信号量、锁、同步块、阻塞队列等机制保证线程安全
    - 安全性
        - 最基础的就是，不要相信任何输入，必须对输入进行先行校验
        - 避免不合法、不合理的输入进入系统中
        - 同时，需要考虑软件是否存在漏洞，修复或避免漏洞被利用
        - 比如常见的软件安全性问题：SQL注入、密码爆破、密码彩虹表破解、明文传输、越权等情况

## 测试与回归

- 测试与回归，主要针对的是集成测试、系统测试、验收测试部分
- 而单元测试、模块测试，本内容则主要在 [编码与实施](#编码与实施) 部分体现
- 这部分，主要分为功能性测试与非功能性测试
- 其中，功能性测试时必须的，这是对核心业务流的完整测试，保证核心业务逻辑的正确性
- 非功能测试则主要是对性能和安全方面的测试，考察性能是否达标，安全是否达标

## 部署与运维

- 部署与运维，主要是提供部署手册与运维手册（QA手册）
- 帮助用户或者运维人员，安装或部署软件，解答软件部署期间可能遇到的问题
- 以及帮助解答软件运行过程中可能遇到的问题，提供相应的解决方案

## 开发指导说明

- 主要提供给开发人员，快速上手，进行继续开发的技术手册
- 主要包含开发环境准备或介绍，软件入口，主要核心业务及对应源码关系，主要核心算法或数据逻辑等
- 也就是，需要哪些环境才能继续开发，或者应该在哪些环境上，或者已经有哪些环境了，各个环境之间的差异是什么，怎么区分环境
- 软件的入口是什么，从哪里开始
- 主要的核心业务是哪些，业务流与数据流
- 关键的算法和数据逻辑，状态转移关系
- 编译、打包、部署的一些常见问题等

## 用户使用手册

- 主要提供给用户，学习使用软件，以及常见问题以及解决方式
- 介绍怎么准备运行环境（如果需要）、数据初始化（如果有）、软件安装、软件启动运行
- 最核心的内容是，从业务流的角度，串接整个软件使用步骤或者过程，提醒关键操作或节点
- 补充常见问题以及处理方式

## 最终输出产物

- 也就是完整的软件，包括程序+数据+文档
- 程序，整个部署安装的程序，可能包含安装程序
- 数据，初始化数据，配置数据等
- 文档，面向不同人员文档，或者软件过程文档，包括以下内容
    - 软件需求文档，单个文件或者归档为一个目录的多个文件
    - 概要设计文档，单个文件或者归档为一个目录的多个文件
    - 详细设计文档，单个文件或者归档为一个目录的多个文件
    - 程序源代码，一般为一个目录或者一个压缩包
    - 软件测试文档，单个文件或者归档为一个目录的多个文件
    - 安全测试文档，单个文件或者归档为一个目录的多个文件
    - 软件部署文档，单个文件或者归档为一个目录的多个文件
    - 软件运维手册，单个文件或者归档为一个目录的多个文件
    - 开发指导手册，单个文件或者归档为一个目录的多个文件
    - 用户使用手册，单个文件或者归档为一个目录的多个文件
    - 工作进度清单，已完成未完成的内容文档，单个文件或者归档为一个目录的多个文件
    - 问题与经验总结手册，记录遇到的问题、经验总结文档，单个文件或者归档为一个目录的多个文件
